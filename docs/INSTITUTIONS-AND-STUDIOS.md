# Establishing a studio in the Village

The studio is part of the main installation. It has its own **Lead Designer**, approved staff, private Library and Archive, working projects and tiny computers. Other institutions can use the same membership, collection and review foundation; the specialised workbench supplied here is for C studios.

The system prepares the residents and their navigation maps. You provide the source projects and creative direction, review lasting changes, and choose how long it may work. You do not need to write individual prompts, manually index your games or run benchmarks.

## First use

1. Install/update from the repository's main installer. Open **Village Institutions.command** in the installed Local AI folder. It opens the local owner page; opening it starts no model work.
2. Create a studio with a name and purpose. For example: “Learn from these two games, preserve their character, and build small original experiments.”
3. Import each C game using its ZIP or a folder on your Mac. Public GitHub imports require a full commit SHA. For a private repository, export/upload its ZIP. Original bytes are retained separately; residents edit working copies. Source files do not have to compile to be studied.
4. Select **Max** mode and start the **founding review**. Its time and turn allowances are visible and finite. It scans indexed source passages, prepares cited explanations of architecture and hardware dependencies, and compares findings. It proposes four initial residents: Lead Designer, Engine specialist, Systems designer and Playtest reviewer. This is inference over your material and approved knowledge, not model-weight training.
5. Review the proposed documents and staff. Approval is the final step for publication or activation. Then review the prepared starting maps. The short maps point to approved knowledge and personal memories; they do not load the entire codebase into every turn. Preparing staff or maps again is available without restarting the analysis.
6. Start **hands-free game planning**. The Lead Designer chooses a game from the studio mission and approved lessons without you providing a genre or prompt. Four design roles explore candidates; the Lead Designer selects one. The tree expands only while consequential design decisions remain unresolved, and a separate auditor reviews each answer. Open the job's **design dossier** to browse questions, answers, checks and bounded design deliverables. This planning job cannot change a project or run code. It can pause/resume if its allowance runs out.
7. Choose **Install pinned studio tools** once. The optional C compiler and Wasm runtime are installed separately from the main model environment. Add the bundled C example, build its cartridge and run its tests to see the workbench in use. The first successful build also measures up to ten instances automatically; results appear under workshop status. No model call is needed for that measurement.
8. After reviewing the dossier, select a project and its Lead Designer, give a direction and start a project session. The design dossier becomes an input to this separate implementation phase; it does not start implementation itself. The resident reads, searches, edits or patches working files, builds, tests, takes notes and requests focused help. Build failures and bounded tool errors return to it to correct; they are not reported as success.
9. Inspect the activity and tasks, run a selected cartridge, save a checkpoint or **Download standalone player**. Unzip the download and open `player.html`; it needs neither a running Village nor a model. Arrow keys, Z/X, Enter and Shift supply controls. Saved games download to your computer.

Starting a new session on the same project carries its working notes forward. Restart, restore, a foreground request, or a resource-mode change pauses background work; resuming is explicit. An exhausted session can receive another hour/128 turns through the page. Local inference has no hosted API charge, but uses your computer and electricity. No GitHub Actions are used by this feature.

The planning department has its own guide: [Studio planning and documentation department](STUDIO-PLANNING-DEPARTMENT.md). It uses four design-role turns and a separate auditor role on the installed local model's serial scheduler. These are bounded agent roles, not four simultaneous models. The host stores every accepted branch and audit so a long plan does not require one huge context. The number of leaves is adaptive; it is not forced to reach 1,000. This stage produces design decisions for the Lead Designer, not implementation tickets.

The middle **Design Integration and Production Planning** department follows design and precedes implementation. It freezes and audits the dossier, inventories decisions, maps them to gameplay systems, and creates reviewed production work orders.
