# Establishing a studio in the Village

The studio is part of the main installation. It has its own **Lead Designer**, approved staff, private Library and Archive, working projects and tiny computers. Other institutions can use the same membership, collection and review foundation; the specialised workbench supplied here is for C studios.

The system prepares the residents and their navigation maps. You provide the source projects and creative direction, review lasting changes, and choose how long it may work. You do not need to write individual prompts, manually index your games or run benchmarks.

## First use

1. Install/update from the repository's main installer. Open **Village Institutions.command** in the installed Local AI folder. It opens the local owner page; opening it starts no model work.
2. Create a studio with a name and purpose. For example: “Learn from these two games, preserve their character, and build small original experiments.”
3. Import each C game using its ZIP or a folder on your Mac. Public GitHub imports require a full commit SHA. For a private repository, export/upload its ZIP. Original bytes are retained separately; residents edit working copies. Source files do not have to compile to be studied.
4. Select **Max** mode and start the **founding review**. Its time and turn allowances are visible and finite. It scans indexed source passages, prepares cited explanations of architecture and hardware dependencies, and compares findings. It proposes five core residents: Lead Designer, Systems designer, Playtest reviewer, Studio Lead and Lead Developer. The Engine specialist is omitted from the default staff proposals; the owner can bring in engine expertise for a scoped work order through a temporary appointment. This is inference over your material and approved knowledge, not model-weight training.
5. Review the proposed documents and staff. Approval is the final step for publication or activation. Then review the prepared starting maps. The short maps point to approved knowledge and personal memories; they do not load the entire codebase into every turn. Preparing staff or maps again is available without restarting the analysis.
6. Choose **Install pinned studio tools** once. The optional C compiler and Wasm runtime are installed separately from the main model environment. Add the bundled C example, build its cartridge and run its tests to see the workbench in use. The first successful build also measures up to ten instances automatically; results appear under workshop status. No model call is needed for that measurement.
7. Select a project, give the Studio Lead a direction, and choose **Start game production**. The saved workflow owns the production lane; legacy `work` requests enter the same controller. For example: “Find the reusable movement and tile-rendering pieces. Preserve the original files in the Archive. Adapt a small playable example to the workstation, test it, and explain what remains unverified.” The Lead assigns Planning, Design Integration and Production Planning, Lead Developer implementation, and independent Playtest in order. Each department saves its result and the Studio Lead explicitly accepts or returns the handoff before the next department can start. Build failures and bounded tool errors return to it to correct; they are not reported as success. For legacy adaptation, use **Guided legacy adaptation** first: select the archived project, describe one small behaviour, and let an agent inspect the immutable archive source. That planning session is read-only. Review its proposed source classification, candidate files, dependencies and test before approving a separate implementation session. The original game stays archived and need not run on the C console.
8. Inspect the activity and tasks, run a selected cartridge, save a checkpoint or **Download standalone player**. Unzip the download and open `player.html`; it needs neither a running Village nor a model. Arrow keys, Z/X, Enter and Shift supply controls. Saved games download to your computer.

Starting a new session on the same project carries its working notes forward. Restart, restore, a foreground request, or a resource-mode change pauses background work; resuming is explicit. An exhausted session can receive another hour/128 turns through the page. Local inference has no hosted API charge, but uses your computer and electricity. No GitHub Actions are used by this feature.

## Legacy adaptation workflow

Adaptation starts from an imported project already in the studio. The agent reads the immutable archived source, not the mutable working copy, during the planning stage. The owner describes one small behaviour or feature and may state what the archive contains, or ask the agent to inspect it. The agent identifies source code, assets, documents, binaries and uncertainty from the files it can actually inspect. If only a playable binary or recording is available, it proposes an observation-based experiment and does not claim to extract original code.

The planning session is enforced read-only in host code: it can inspect the selected source tree and bounded source passages, consult approved knowledge and read the SDK. It cannot edit, build, or run the original game. Its result remains a draft. The owner reviews the plan and explicitly approves it before the studio starts a governed production workflow against the project's working copy. The immutable archive remains unchanged. The implementation agent adapts the smallest slice, builds and tests it on the C console, and reports what was observed, inferred and left unverified. This workflow does not promise that the original game can run on the console.

## How the studio works

**Sources and seeding.** Import records include hashes, provenance, text and a lexical symbol index. ZIP traversal, links, devices and case-colliding entries are refused. Archive originals are preserved even when hardware-specific code is removed from a working copy. Founding studies bounded passages rather than pretending to understand 200,000 lines in one context. Its final comparison uses a bounded selection of its findings; it is not an exhaustive proof that two complete engines have been reconciled. Builds and behavioural evidence remain separate from source interpretation. Additional projects can be imported and studied later.

**Knowledge and memory.** Studio publication goes to its private collection. General Village requests do not gain that access. Staff have approved instructions, fast-access own memories, a deeper-memory glossary, and preferred document pointers. Publishing a memory/document and approving its placement on a map are separate decisions. Residents can search and follow references when needed. Working files, task notes and session notes are drafts, not approved personal memories. Source withdrawal withholds dependent directions. Activity records show the supplied source/context and output; they do not claim to reveal a model's hidden reasoning.

**Roles and collaboration.** The owner can message the Studio Lead from the Institutions page; Village Captain can use `studio_contact` to list studios, send a message, and retrieve the saved thread. Both messages enter the same durable inbox. The Studio Lead runs the whole institution and manages Lead Designers and Lead Developers, using project tasks, approved resident memory, the studio Archive and recent conversation history. It assigns project design and acceptance criteria to a Lead Designer, and technical delivery to a Lead Developer. Messages wake bounded local sessions automatically; queued Studio Lead/worker/curation work resumes after an ordinary gateway restart. Explicit Pause still holds queued work until resumed. Lead Designers own project design direction. The Systems designer prepares test checkpoints and the Playtest reviewer verifies them. The Engine specialist is omitted from the default staff proposals; the owner can bring in engine expertise for a scoped work order through a temporary appointment. All roles are proposed first and require owner approval. A Studio Lead cannot curate their own learning.

### Staged project workflow

Every game production uses one durable staged workflow. This reconciles the leadership queue and production loop into a single controller backed by `studio_workflows`; there is no separate advancing production loop or duplicate production state table. Exactly one active game is allowed per studio, across all projects. Paused, blocked, awaiting-review and human-review work retains that slot until final closure or explicit owner cancellation. The required order is:

1. **Planning Department — Lead Designer.** Inspect only the selected immutable archive source. Save a reverse scaffold in bounded checkpoints with exact source citations: archive contents, control/data structure, reusable gameplay or data, hardware dependencies, unknowns, and a small candidate experiment. This stage cannot edit or build.
2. **Design Integration and Production Planning Department — Systems designer.** Turn the scaffold into explicit test cases and acceptance criteria, saved as workflow checkpoints. Give each case observable state, available actions, reset/starting state, deterministic seed and bounded input sequence, success/failure conditions, expected state or screen outcomes when supported by evidence, metrics or hashes, and resource/time limits. State whether AI can execute each case with current instrumentation; identify visual evidence needed, human-only questions and verification blockers. This stage cannot edit or build.
3. **Implementation Department — Lead Developer.** The host permits this handoff only after the Design Integration and Production Planning Department assignment completes and the Studio Lead accepts its handoff. The Lead Developer owns technical execution and may create up to three bounded implementation or analysis subtasks over the assignment, one at a time. Each child task is durably linked to its parent assignment and the Implementation phase, receives the same Planning and Design Integration and Production Planning checkpoints, and reports back to the Lead Developer. The Lead Developer waits for each report before assigning another child or editing, building, or testing the shared project. Use team_status to review results; the Implementation phase remains open until every subtask is complete or blocked and the Lead Developer consolidates the findings.
4. **Review — Playtest reviewer.** An independent, read-only resident validates the build, replays the Design Integration and Production Planning test checkpoints, reproduces implementation claims, and performs bounded exploratory checks. The reviewer saves a structured report with build identity, source digest, runtime/resources, every test's seed/inputs/expected and actual result/status/evidence, reproducible findings, unverified questions and an explicit verdict. Every test is passed, failed, blocked or not testable. Findings distinguish Observed, Inferred and Unverified evidence.

The verdict proposes the next route for Studio Lead review: `verified` permits Studio Lead closure; `return_to_implementation` restarts implementation; `return_to_middle` returns to Design Integration and Production Planning; `return_to_planning` returns to the Planning Department; `human_review_required` records a human-only question and keeps the workflow open for human review; `blocked` holds the verification phase for a retry. Revised Design Integration and Production Planning checkpoints must link to the failed Playtest report before implementation can resume. A verification assignment cannot complete its workflow phase without a structured report. The host rejects `verified` unless the build succeeded and loaded and all supplied tests passed. After a verified report, the Studio Lead may override its route back to Implementation; the workflow history links that override to the report ID and reason.

A completed department assignment enters `awaiting_review` in the same phase. The Studio Lead reads its saved checkpoints and report, then calls `workflow_review` with `accept` or `revise` and an evidence-based reason. Acceptance applies the proposed next route. Revision keeps the same department active and saves feedback for its replacement assignment. After accepted Playtest, `ready_to_close` requires a final Studio Lead review through `workflow_close` or `workflow_return`. A department cannot advance itself. Failed jobs block the workflow; the Studio Lead can retry that stage while preserving its previous report. Only the Studio Lead can start, review, route, retry, return, or close a workflow. Owner cancellation is available after pausing studio work and waiting for running jobs to drain. Cancellation retains checkpoints, reports and history while releasing the production slot. An active, blocked or human-review workflow blocks ordinary project assignments that would bypass its gates.

Workflow records, stage reports, cited checkpoints, structured verification reports and their hashes appear in the studio view and project provenance manifest. Recovery verification checks these records along with builds, checkpoints and evidence. Checkpoints are capped at 64 per workflow; each has a short title, bounded body, validated evidence references and, for revised checkpoints, a link to the failed verification report. Use the Studio Lead chat to start and manage the workflow; it is not a separate interactive department UI.

The Studio Lead uses `workflow_assign` to create the current department assignment and queue a separate resident job. The `delegate` action is reserved for a Lead Developer's specialist subtasks within Implementation. The Lead Developer owns technical delivery and can dispatch up to three scoped specialist tasks over an assignment, one at a time. Subtasks retain their parent, assignee, status and report in the workflow record. After dispatching a specialist, the Lead Developer job saves a `waiting` checkpoint and releases its execution slot. The specialist runs serially, saves its report, and wakes the same Lead Developer job with its remaining budget and context. The Lead Developer reviews results with team_status and closes the assignment only after every child is complete or blocked. In a staged workflow, the parent and all children are linked to Implementation; the Studio Lead advances to independent Review only after the Lead Developer completes that handoff. A separate Playtest Reviewer assignment uses a host-enforced read-only mode: it can inspect, build and run available checks, but cannot edit or patch. Assignment results return to the Studio Lead inbox, and pending learning is automatically sent through a bounded curation job. Each job has finite time/turn limits and uses the local Captain model; project build/test execution remains in the studio workbench sandbox.

**Temporary Village appointments.** An owner can propose an appointment for an existing Village resident and name its sponsor, role, title, expiry and one open work order in one project. The proposal remains pending until the owner reviews and approves it. Approval adds no institution membership or grant. The resident can then be started explicitly on that appointment, with access restricted to the named project and work order. The appointment expires, can be revoked by the owner, and closes when the assigned work is completed. Its work packet omits institution documents, resident lists, source catalogs and studio memory. It can inspect/edit the project working copy, build and run the project’s available checks, then submit project-scoped learning. This is an owner-started appointment, not automatic dispatch.

**Learning and review.** Resident work closes with either a learning record or an explicit statement that there was no reusable learning. Learning records identify scope, work order and the submitter’s evidence note. After delegated work completes, the Studio Lead automatically reviews eligible records; accepted lessons are stored in the studio Archive and included in later permanent-resident work packets. The evidence note remains an agent-submitted claim, not host verification. Ordinary internal work among approved residents no longer needs the owner to start each assignment. Temporary Village appointments and permanent knowledge/membership still require owner review; temporary appointments also require explicit start and are not auto-dispatched. The studio does not outsource, use cloud inference, install packages on behalf of residents, or expose a general shell/network tool.

**Concurrency.** At most four studio jobs run, using the existing shared local inference scheduler. A project has one active owner session. Founding, Commons and studio sessions have admission checks to avoid running their separate background modes together. A helper is a bounded turn within its owner's job, not a fifth model. Machine instances are separate from speaking agents: up to ten per institution, forty across the host. Idle machines do not run simulation steps. Each studio runs one department or manager job at a time. Up to four different studios can use the background slots. Specialist jobs suspend and resume their parent instead of competing with it for the same studio slot.

## The tiny computer

The target is portable C compiled to WebAssembly, with a **320 × 180** framebuffer and fixed 60 Hz simulation steps. The downloadable player uses integer nearest-neighbour enlargement: six times the internal resolution fills a 1920 × 1080 image. Its controls and page furniture need additional space. No Game Boy cartridge compatibility or emulator is required.

The SDK provides pixels, rectangles, four simple tone channels, numbered binary assets, saved data and diagnostic metrics. Implement `vm_init(seed)`, `vm_update(buttons)` and `vm_draw()`. Drawing must leave simulation memory unchanged so headless tests can skip intermediate frames. A `studio.json` manifest lists C sources, assets and tests. The bundled example is a complete reference. Residents have an SDK-read action and can build engine layers in C on top of it.

The bundled `village_graphics.h` adds indexed-colour sprites with transparency and integer scaling, camera-based tile rendering, bitmap text using a project-supplied font, and rectangle collision checks. These are ordinary reusable C functions, so residents can inspect and adapt them. They do not have to rebuild those basics for each experiment. Sprite animation can select successive atlas regions; menus and game-specific rules remain project code.

Drawing may use temporary C stack data. The host and exported player restore memory/global writes after drawing, retaining the rendered output. Persistent changes belong in updates. Drawing cannot grow memory or modify saved-game data.

This is a freestanding C target, not a complete operating system or an automatic compatibility layer for every old engine. Standard-library dependencies, hardware registers, interrupt handlers, bank switching and original cartridge/linker assumptions need adapting in the working copy. Useful gameplay, data structures, algorithms and engine code can remain. The owner can try an original Makefile in the macOS build sandbox and inspect its diagnostics; that does not promise an arbitrary historical build will run, or emulate its original hardware. Original native executables are not exposed as an unrestricted resident-run tool.

The version-one save format supports linear memory and exported globals, not mutable function tables. Function-pointer-heavy engines may need an explicit dispatch layer. The SDK does not yet include a pixel-art editor or a 3D Village renderer. The framebuffer/input boundary leaves room for a future in-world screen.

## Execution, tests and resources

A machine executes only the SDK imports: no WASI filesystem, process or socket capabilities. Each entry has instruction fuel, drawing charges and memory bounds. A batch advances at most 600 steps and yields between groups of four. Diagnostic values, state/screen hashes and exact input history let residents test behaviour without continuously sending screenshots to an LLM. A resident can request an actual screenshot for local visual inspection; this explicitly fails if the configured model does not support images. Passing metric assertions is not a claim that visual design is good.

Each successful build retains a source snapshot, hash, report and portable cartridge. Experiments can reset to a seed, save or restore state, and replay bounded input sequences. Explicit saved checkpoints have separate identities from automatically updated recovery state. Withdrawn projects cannot continue running through an already-loaded machine. Machines are not automatically restarted after a gateway restart.

The old strict Game Boy CPU, RAM and cartridge limits were removed. Current host defaults are 16 MiB guest memory, 16 MiB code plus assets, 1 MiB saved game data, a 256 MiB project and 1 GiB institution directory. Builds are serial, bounded to 120 seconds, limited in output size and isolated by macOS `sandbox-exec`; no unrestricted production fallback exists. The shared machine worker uses a 200 ms/second CPU token bucket, with bounded bursts and a 1 GiB RSS threshold checked at request completion. That is a worker budget, not a promise about whole-system usage or transient memory peaks. Inference and compilation consume additional resources.

Automatic calibration reports measured CPU time, elapsed time, guest memory and peak worker RSS for the first real cartridge. Results persist across restarts. Up to ten loaded instances are sampled sequentially; this is not a claim that forty busy instances have been benchmarked, nor that every project runs 100 times faster. More complex cartridges can consume more time. Stop/pause remains available. When a quota is reached, work stops with an explanation rather than deleting original material automatically.

## Build and save compatibility

Every new build writes a versioned `build-manifest.json` beside its immutable source snapshot. The cartridge embeds the same manifest: manifest schema, SDK and ABI, cartridge and save-format versions, compiler and Wasm runtime versions, compiler flags, source-file hashes, asset hashes, and the overall source hash. The workbench and downloaded player report unsupported cartridge/ABI/save versions rather than trying to guess how to run them. Existing format-1 cartridges without a manifest remain readable as legacy version one.

Checkpoints identify their envelope, build manifest, SDK ABI and save format. On restore, the workbench first migrates a copy, restores it in the runtime, and compares the resulting state with the candidate. Only after verification does it retain the original bytes under `machines/originals/` and write the migrated checkpoint. Unsupported formats, ABIs, or build identities stop with a clear error; the original file is left intact. Automatic recovery checkpoints are quota-checked, including replacements, so they count against the institution's storage budget without charging twice for the prior checkpoint.

## Recovery and withdrawal

Studio records, originals, approved references, working files and saved machines live under the Village data root and are included in the existing encrypted workspace backup. Each project has a small provenance manifest connecting its immutable original, working-copy revision, builds, checkpoints and experiment evidence by hashes. The Workbench can display that manifest and run a recovery check after restore; it reports missing or changed artifacts, and runs only when the studio jobs are paused. On an ordinary process restart, durable manager, assignment and curation jobs are queued for recovery. A waiting Lead Developer resumes when its specialist report is available. Explicit owner Pause still holds queued work until resumed; machines require explicit restoration. Incomplete uploads are excluded. Downloaded players and their saves are external copies and are not automatically backed up or recalled. The download action displays this boundary and adds the export hash and status to the project manifest.

The studio page's **Withdraw a source** previews the exact affected project, withholds derived directions and preserves original archive bytes. Withdrawal is not erasure.

The existing **whole-Village source erasure** is deliberately much broader: it now also deletes all institutions, studio originals, residents, projects, builds and saves because uncited copies cannot reliably be attributed. Its final preview states this scope. Use withdrawal when you only intend to stop using a studio reference. External downloads/backups are outside managed erasure.

## Validation boundary

Real C compilation, Wasmtime execution, replay/checkpoints, local worker transport, fuel traps, forbidden imports, scopes and owner review are tested using authored fixtures. Offline player logic is also exercised with actual Wasm. The authoring host is not your Mac: native sandbox execution, installer permission dialogs, browser layout, your two games and sustained local-model performance are not represented as tested. The runtime compiler fixture is Clang; the pinned production compiler is Zig. Optional native tooling must pass its build on the actual Mac before a project can run. Missing native acceptance is engineering validation, not an instruction for you to manually create all the residents.


## Portable experiment evidence (Workstream 3)

Each cartridge machine session writes a compact, versioned JSON evidence record beneath that build's `evidence/` directory. The record links its project, build manifest and source hashes, seed, bounded input sequence, latest metrics and state/screen hashes, and any cartridge test assertions. Studio work packets include recent records so residents can cite them. Findings use exactly three labels: **Observed**, **Inferred**, and **Unverified**. Observed and Inferred findings must cite evidence record IDs from the same project; Unverified findings may state what still needs a build or playtest. Records preserve claims and citations, not hidden model reasoning.

Input sequences are capped at 2,048 actions per record; assertions and findings are capped at 64 each; records are limited to 256 KiB and 500 records per build, and count against the institution storage quota. Screenshots are omitted by default. An owner may opt in for a work session using “Retain screenshots in experiment evidence”; each retained PNG is capped at 256 KiB. Machine checkpoints and downloaded players do not include these evidence records. Records live with their build and are preserved by normal project backup and restore.


## Project provenance and restore verification (Workstream 4)

The project-level `project-manifest.json` is stored beside the working-copy directory. It references, by path and SHA-256, the imported original archive, current working-copy revision and files, each build snapshot/manifest/cartridge/report, machine checkpoints (including preserved pre-migration originals), approved Library documents and studio archive entries derived from that source, and experiment evidence records. It records external player exports as external copies with their package hash and an explicit note that backup and withdrawal cannot recall them. The manifest holds metadata and hashes rather than duplicate game or save data.

Use **Show provenance manifest** to inspect the links. After restoring a workspace backup, pause studio work and run **Check restored project**. The check compares the stored manifest with the files present and reports the artifact groups that differ; it does not silently rewrite a mismatching manifest. Jobs must remain paused during the check. Existing projects receive an initial manifest when the studio service starts after upgrade, so subsequent backups have a baseline to verify.

### Reconciliation and validation boundary

The canonical production record is the saved workflow and its department assignments. Studio Lead/Captain inboxes, approved appointments, scoped learning, versioned builds/saves, archive provenance and recovery checks are retained. The install manifest includes `studio_roles.py`, and an isolated import test checks the copied installation without the repository on Python's search path.

Controller integration tests use scripted model replies and authored verification payloads to exercise actual queued jobs, serial specialist edits, saved checkpoints, stage review and final closeout. They do not establish real-model design quality, compilation or visual acceptance. Stronger binding of verification claims to actual build, run and image evidence remains a separate production-reliability change.
